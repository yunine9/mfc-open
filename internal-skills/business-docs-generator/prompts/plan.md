# 规划阶段提示词

## 一、目标

在 module_id、scope 和用户本轮要求界定的业务范围内，先按 [源码研究范围](../references/research-scope.md) 自动定位各仓的相关目录，再穷举其中的业务入口、场景、实际依赖与功能，生成完整文档规划。共享仓里的其他业务不因位于同一仓就进入产物范围；必要共享实现沿本业务调用链核实。先按 [平台执行约定](../references/platform-execution.md#规划与路径) 确认每个 target.docs_path、模块入口及旧任务布局，再分配调查。调查与规划核查涉及上传资料或无线概念时，先读 [来源方法](../references/business-sources.md)，按其建立索引并回读原文。

## 二、执行步骤

1. **列仓并确定本业务目录**：
   - knowledge_structure 省略 repository_id 仅列仓；逐仓用 component_source list 的当前层结果及业务关键词 search 定位相关入口。按需要展开命中目录，不递归列完公共仓才开始判断范围；默认过滤的依赖与生成目录不当作自有业务模块
   - 列出全部关联仓及其对本业务的作用，分别记录本业务实现目录、按需依赖、归属依据与待核实项。公共仓不因尚未定位就采用全仓范围；某仓没有本业务实现时，核对实际依赖角色即可
   - 读取确认业务入口、构建目标和技术栈所需的构建/注册文件（如 `pom.xml`、`package.json`、`CMakeLists.txt`），不遍历公共仓全部构建单元
   - 查看 context.materials 的资料状态、版本/digest 与范围摘要；需要目录时 knowledge_material({}) 取得章节、包内文档、图片和警告，分配相关资料编号及待核对问题，不在主会话展开全部正文

2. **分配独立调查，再深入源码**：
   主会话依据已定位的本业务目录与入口划分调查单元，不先把全部业务实现读入自己的上下文。按业务入口及完整场景细分；同一场景的关键调用链保持完整，不按任意行数截断。每个单元说明仓编号、本业务目录、按需依赖、用户限制、具体待回答问题、依赖单元和对应产物；共享库仅调查本业务实际使用部分。调查步骤通过 knowledge_work schedule 登记 readonly=true，互不依赖的单元可用 run 的 concurrency=1～4 并行执行，本方法默认 3。可执行的参数与结果示例见 [独立调查](../references/platform-execution.md#独立调查)。

   以下深入读取由对应独立调查单元完成：
   - 读取构建文件识别技术栈（语言、框架、构建工具）
   - **深入本业务源码目录**，不可仅看顶层目录名就推断功能结构。进入相关子目录并沿入口追踪必要共享实现，识别真实划分，不要求逐个展开共享仓中无关业务的目录
   - 对于 Java 仓：从实际源码根目录识别入口、业务实现及存在的分层，常见位置如 `src/main/java/`
   - 对于 C++ 仓：从构建目标与实际源码目录识别业务模块，不能假定所有文件都在 `src/`
   - 对于前端仓：从实际路由/页面/状态入口识别业务，`src/containers/`、`src/components/`、`src/store/` 仅为常见示例
   - 其他语言同样按构建、入口和调用实现调查；记录真实核心类/函数及关键文件，不套用固定目录或分层

   instructions 只传本单元范围、方法入口、证据索引和问题。单元启动时按 id 回读必要结果并重新打开原始源码与相关资料；不熟悉的无线概念先查已有证据，再按具体问题补查背景。knowledge_work_result 的 summary 只写主要发现，data 保存关键路径/行范围、跨仓调用与待核实问题，业务来源按来源方法保存 source_index、source_gaps 和 source_conflicts，document_ids=[]。结果由平台持久保存，只读单元不调用 save_document。主会话按编号读取必要结果，维护短摘要与编号引用；发现尚未调查的范围时继续登记具体单元，不集中展开全部源码或资料。

   每个范围内目录和业务入口应归入已调查功能，或说明不相关/生成内容的依据。尚未调查、无法读取和来源失败单独列为待解决范围，不计作已穷尽。调查不要求机械逐行扫描几十万行源码，但必须沿完整入口清单追踪有关实现，不能用若干代表性入口替代全部功能覆盖。

3. **识别跨仓关系（穷举所有调用链）**：
   - 公共仓按已定位目录中的构建/注册文件、import/include 和实际调用确认依赖。knowledge_structure 的扫描范围及适用条件见源码研究范围方法；不为获得候选而默认扫描全部关联仓
   - 各调查单元通过构建依赖、IDL、REST 路径、import/include 及调用实现识别范围内仓间关系；主会话汇总有来源的关系，待确认的双方调用交给独立调查核实
   - **穷举本业务实际交互的外部系统**，包括但不限于：
     - 独立数据库或数据库服务；进程内数据库和本地 SQLite 记录为存储机制，不自动视作独立系统
     - 文件存储（NFS、HDFS、HOfS 等）
     - 消息/事件中间件（CORBA Event Service、Kafka 等）
     - 独立认证/权限服务；进程内安全库记录为技术依赖
     - 命名服务（CORBA Naming Service 等）
     - 其他平台服务（拓扑服务、网管服务、配置管理等）
     - 网元设备（通过各类协议对接）
   - **不可仅列出最明显的外部系统。** 检查本业务在各仓的网络/消息/存储交互点。第三方 import 或构建依赖只是线索；进程内工具库不是独立外部系统，不为它生成虚构的协议和系统画像
   - 用 PlantUML 画出有证据的仓与外部系统关系；没有关系的仓可作为独立节点。复杂关系可分图并保留衔接，不能为了图小删掉真实节点

4. **识别业务域（穷举范围内业务意图与完整链路）**：
   - 从实际业务入口出发：页面操作、公开 API、命令、定时任务、事件或消息消费均需覆盖。存在前端/BFF/核心分层时沿该链路追踪；没有这些层时不补造
   - **穷举本次业务范围内的业务域，不可遗漏。** 任务管理、结果查询、导入导出等只是可能的业务分类；不按这些示例扩展到共享仓中无关业务
   - 对于每个业务域，列出：
     - 涉及的仓（完整列表）
     - 核心链路（一句话描述端到端流程）
   - **业务域判断标准**：一组围绕独立业务意图、具有完整数据流的功能构成业务域，可跨仓，也可仅落在一个仓。按业务边界合并相关场景，不按仓数或函数数量硬拆；不可因为功能"较小"就省略

5. **规划文档列表**：
   - 按文档类型列出所有待生成文档，并另行标明真实执行依赖；不能把阅读导航的顺序变成整包串行执行
   - 每个文档标注 layer（domain / repository）、对应模板；templates/repo 是模板目录名，不是 layer 值
   - directory-v1 时，所有文稿位于相应目标的最终 target.docs_path 内；领域目录默认 `Function_Knowledge/Access Function/<模块名>`，代码仓目录默认 `docs/<业务名称>`，以平台实际目标为准。领域与代码仓入口为同目录 README.md，领域详细索引为 index.md。代码仓根 AGENTS.md 与领域目录内 AGENTS.md 均由平台生成，不列为模型产物。旧任务按当前保存位置规划，平台整理后采用新路径。编程规范只描述本业务适用情况或引用已存在的仓级约定，不声明由本任务统一全仓规范
   - **领域文档**：标注需要通读的仓列表及各仓的业务源码范围
     - 已确认入口与关键实现使用实际仓编号、文件或符号定位，例如 `repo-api:src/task/TaskController.java#create`；相关模型、配置继续列出。待展开目录另列为未核实范围，不把目录名冒充完成的精确调查
     - 范围覆盖实际存在的入口、业务实现、模型、状态与配置。采用 Controller/Service 等分层时逐层核对，非分层或函数式代码按真实结构记录，不补造类
   - **仓级文档**：标注该仓内需要覆盖的**业务功能**及每个功能涉及的源码范围
     - 已确认入口与关键实现定位到实际文件/符号，说明它们如何构成该功能；目录只用于标注所属范围或仍待展开的区域
     - 一个业务功能可能跨多个源码目录，须列出所有相关目录和关键文件
   - **模块划分维度：按业务功能划分，不按代码目录划分**。模块文档名使用业务功能名（如 `trace-task-create`），不使用代码目录名（如 `domain-task-create`）。一个业务功能可能跨多个代码目录，合并为一个模块文档。
   - **穷举本业务的所有功能**，不可遗漏。各仓功能文稿覆盖本次 scope 内全部业务逻辑，不可只列主要功能而省略次要功能；不要求覆盖同仓其他业务
   - 每个调查单元保留去重后的业务入口到功能/场景的对应关系。多个入口可以服务同一功能，一个入口也可能有多个真实场景；说明对应关系，不要求入口数量等于功能数量
   - 在执行关联中保留相关调查单元编号，写作步骤据此定位原始来源；每篇开始时回读对应源码和资料，不把协调器摘要当作本篇已经完成的阅读
   - 最终导航同步单独安排：每份模块目录导航依赖其覆盖的全部文稿写作及最后修订步骤；已有初稿时依赖初稿步骤，没有则可直接生成最终版。领域入口列出各仓模块 README.md 时也依赖这些目标；不同导航不要循环等待。声明全部实际改动编号，导航步骤不包含平台生成的 AGENTS.md

6. **保存并登记完整规划**：按 `prompts/plan-template.md` 保存 Markdown，使用 knowledge_work save_document，id=current-plan。正文保留全部产物条目、范围边界和调查结果编号，不复制源码或全部调查报告。填写稳定 document_id、实际 target_id、仓内 path、模板及写作步骤；instructions 带本条目必要字段和证据索引，不要求每个 writer 加载整份规划。用 knowledge_diagram_check({work_document_id:"current-plan"}) 查图，按 next_start 读完报告；invalid 修正正文再查，unavailable 保留规划与依赖问题。图通过后用 action=plan、work_document_id=current-plan 登记全部 document_ids，宿主登记前也会校验。规划不进入知识发布；已登记产物是否齐全由宿主检查，业务完整性仍需独立核查。

7. **独立核查**：主会话按 [规划核查配对示例](../references/platform-execution.md#规划核查) 登记 readonly=true 的步骤，省略 expected_document_ids 与 step.review。核查读取本提示词、规划模板、current-plan 和 read_plan 全部清单/排除说明分页，用 knowledge_diagram_check 的 work_document_id=current-plan 读取当前图表报告，按调查索引回查各仓业务入口和相关资料中的业务范围。核对清单与正文一一对应、入口到功能/场景有对应、适用文档类型齐全；不能把未读资料、来源失败或无线通用背景当成已经确认的系统范围。大范围可分仓或业务域核查，主会话汇总各范围结论。核查结果通过 knowledge_work_result.review: {pass, feedback} 返回，document_ids=[]，省略 status；图 invalid/unavailable 或来源阻碍返回 pass=false 和具体原因，仍可保存结论。普通只读步骤的 done 只表示返回结果，主会话须检查结果的 review.pass。规划实质修订后才安排新一轮核查；中断或执行配置修正接续原步骤，不重建规划或重复既有调查。新发现先补正文和 plan；旧排除项保留原因。

## 三、规划输出格式

使用 `prompts/plan-template.md` 模板生成规划文件。

## 四、自检清单

规划完成后，逐项自检，不通过则补充后再次自检：

- [ ] **仓范围**：每个来源仓是否已定位本业务目录及入口，或说明只提供依赖/没有本业务实现的依据？是否把公共仓全目录或未定位的范围当成整仓研究任务？
- [ ] **业务域完整性**：实际页面、API、命令、定时和事件入口是否都能对应到业务域/场景？是否遗漏无前端或单仓业务？
- [ ] **外部系统完整性**：实际独立数据库、存储、消息、认证和命名服务是否覆盖？是否把进程内库或本地存储误作独立系统？
- [ ] **源码范围精度**：已确认入口和关键实现是否有文件/符号定位？待调查目录、来源失败是否仍明确标为未完成，未被算作已经精确覆盖？
- [ ] **模块命名**：所有模块文档名是否表达业务功能，而非机械复制目录名？技术词只有在确为业务名称且有依据时保留，不能只因包含某个词就判错。
- [ ] **模块覆盖度**：是否覆盖所选业务在各关联仓的全部入口和功能？是否遗漏本业务场景，或无依据地扩展到同仓其他业务？
- [ ] **模板符合性**：保留规划模板的主要章节与执行关联；示例仓、接口和功能按实际清单展开，没有为凑示例数量补造条目？
- [ ] **输出覆盖**：是否列全范围内基础文档、各业务域、真实交互仓对、外部系统与各仓业务功能？经验文稿仅在有真实案例时规划。
- [ ] **执行对应**：每篇是否有唯一稳定文稿编号、目标编号、仓内路径和写作步骤编号？directory-v1 时是否全部位于各自最终 target.docs_path 内、包含同目录 README.md 入口，AGENTS.md 是否由平台生成？旧任务是否沿用当前保存的实际文稿路径？是否将逻辑仓前缀误当作仓内路径？

## 五、约束

- 规划阶段保存规划过程文稿，不生成待发布的知识正文
- 规划通过独立核查后无需用户确认，直接登记全部写作步骤并自动生成
- **穷举原则**：本业务范围内的关联仓职责、业务域、外部交互和功能都必须覆盖，不因"较小"或"次要"省略，也不因共享仓关系扩大到其他业务
- **精度原则**：扫描源码时必须深入到类/文件级别，不可仅看目录名就推断模块结构。
